    Three live experiments that run real threads and processes on this computer. Each one shows a concept the scheduler depends on.

    1 · Race condition and Lock threading.Thread, threading.Lock

    Several threads each add 1 to the same counter many times. Adding is really three steps: read the value, add 1, write it back. If another thread runs between the read and the write, one update is overwritten and lost.

    time.sleep(0)

    time.sleep(0) forces a thread switch at the worst moment, standing in for real work such as a database call. Without it the bug still exists, but shows up only rarely, which makes it hard to catch. The lock is correct every time, but slower: threads wait their turn.

    2 · The GIL: threads vs processes concurrent.futures ThreadPoolExecutor / ProcessPoolExecutor

    The same jobs are run three ways: one after another, with a thread pool, and with a process pool. CPU-heavy jobs do maths the whole time. IO-heavy jobs mostly wait, like a download or a disk read.

    Python's GIL (Global Interpreter Lock) lets only one thread run Python code at a time. A thread that is waiting gives the GIL up; a thread doing maths keeps it.

    Takes about 10 seconds.
    • Run the benchmark to see results.
    3 · Semaphore: limit how many run at once threading.Semaphore, threading.Barrier

    All threads start at the same moment and want the same resource, for example the disk. A semaphore lets only N threads in at a time; the rest wait outside until someone leaves. The scheduler uses one so that at most 2 file jobs run together.
